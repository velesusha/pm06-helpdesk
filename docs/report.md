## Назначение и результат работы

Подготовлена учебная система заявок ИТ-службы колледжа. Приложение позволяет оператору зарегистрировать обращение и назначить исполнителя, исполнителю обработать назначенную заявку, администратору управлять пользователями и категориями. Система сохраняет историю действий, рассчитывает приоритет по правилам и поддерживает повторный импорт без дублирования.

Исходный проект и учебный набор данных созданы с нуля по картам практики. Реализованы локальный HTTPS и подключаемый адаптер SQL Server. Фактические автоматические и браузерные проверки выполнены на SQLite. Проверки SQL Server, создание файла .bak и восстановление в SSMS необходимо выполнить на стенде колледжа. Они не включены в число пройденных автоматических проверок.

Подписи, оценки, факт прохождения инструктажа, реквизиты выписки из реестра и протокола испытаний заполняются по реальным сведениям и подтверждаются руководителем практики.

## Характеристика объекта практики

Объект — процесс приёма и обработки обращений сотрудников по вопросам оборудования, программного обеспечения и сети. Основной документ системы — карточка заявки. У заявки есть внутренний номер id, исходный номер source_id при импорте, тема, описание, категория, кабинет, статус, исполнитель, автор и временные отметки. Для определения приоритета используются недоступность сервиса и число затронутых пользователей.

Учебный стенд включает браузер, Python 3.10 или новее, приложение app.py и СУБД. При работе по полному заданию используются SQL Server и SSMS. Для локальной демонстрации предусмотрена SQLite, входящая в стандартную библиотеку Python. Интерфейс написан на HTML, CSS и JavaScript без внешних веб-сервисов.

При конфликте состояния сервер отклоняет устаревшее изменение. Для контроля восстановления сравниваются число записей, id, source_id, статус и исполнитель.

Требования к защите: проверка ролей выполняется на сервере, а не только в интерфейсе. Пароли сохраняются как PBKDF2 SHA-256 с отдельной солью и 260000 итерациями. Сессия живёт 8 часов и хранит хеш случайного токена. Cookie имеет HttpOnly, SameSite=Strict и Secure в HTTPS-режиме. Изменяющие запросы проверяют CSRF-токен. На локальном стенде используется самоподписанный сертификат; сервер слушает только 127.0.0.1.

Требования к входным данным: CSV в UTF-8, разделитель точка с запятой или запятая, заголовки source_id, subject, description, category, office, service_unavailable, affected_users. Пустая тема и неизвестная категория отклоняются. Исходный номер отделён от внутреннего идентификатора базы. Максимум 2000 строк на один импорт.

Требования к окружению: Python 3.10+, браузер, пакет cryptography для HTTPS. Для SQL Server дополнительно требуются pyodbc, ODBC Driver 18 и доступная база с корректно настроенным TLS. Фактические версии программ на стенде: [заполнить после установки].

Порядок правил важен: критический случай проверяется до высокого. Граничные значения 4 и 5 входят в test_04. Правило не использует стороннюю модель и воспроизводимо при каждом открытии карточки.

### Карта 13 Обновление и порядок отката

Перед обновлением нужно остановить изменение данных, записать текущий Git-коммит и версию СУБД, сохранить полную резервную копию и выгрузку заявок. Затем установить код v1.1, запустить приложение и проверить прежние заявки, фильтры и вычисление приоритета. Версия 1.1 использует существующие таблицы и обновляет запись metadata; удаления или преобразования заявок не выполняются.

Порядок отката: остановить обновлённое приложение, вернуть код тега v1.0, подключить отдельную БД, восстановленную из копии до обновления, и повторить вход и сверку. Исходная БД при пробном восстановлении не перезаписывается. В SQL Server используются BACKUP DATABASE, RESTORE VERIFYONLY, RESTORE FILELISTONLY и RESTORE DATABASE с MOVE. Готовые заготовки находятся в sql/backup_restore.sql.

Журнал SQL Server: исходный коммит [хеш]; копия до обновления [путь дата SHA-256]; версия до [значение]; версия после [значение]; контрольная выгрузка [путь]; фактический результат проверки [заполнить на стенде].

### Карта 14 Пробное восстановление

На демонстрационной SQLite проверяются целостность копии, восстановление в новый каталог, совпадение id, source_id, статусов и исполнителей, очистка прежних сессий и новый вход. Эти действия входят в test_14. Для SQL Server требуется отдельный протокол, поскольку формат .db не заменяет .bak.

Перед восстановлением в SSMS проверяются источник и дата копии, её читаемость, имя целевой базы, логические имена файлов, свободное место, права SQL Server на каталог и пути MOVE. Восстановление выполняется в новую Pm06Helpdesk_Restored. Затем приложение версии 1.1 подключается к ней и выполняется вход. Отсчёт начинается перед восстановлением и заканчивается после успешного входа; предел по заданию — 30 минут. После входа сверяются число, номера, статусы и исполнители заявок.

Ответы на вопросы приложения 4: резервная копия нужна для возврата данных после сбоя; перед обновлением записываются версия, коммит, имя базы, время, копия и контрольные данные; успех подтверждают вход, сохранность записей и работа изменённых функций; в SSMS проверяют источник, цель, файлы, место и права; сверку проводят по контрольной выгрузке, время фиксируют от начала восстановления до входа.

Протокол SQL Server: начало [дата время]; конец после входа [дата время]; длительность [мин сек]; число заявок до и после [значения]; расхождения по номерам, статусам и исполнителям [результат]; адрес и версия стенда [значения]; файл копии [путь]; ответственный [ФИО].

## Материалы к картам 15 и 16

### Карта 15 Руководство пользователя

Вход: откройте адрес стенда, введите логин и пароль, нажмите «Войти в систему». При неверном пароле проверьте раскладку и повторите попытку. После нескольких неудачных попыток подождите минуту. Для завершения работы нажмите кнопку выхода в правом верхнем углу.

Оператор: нажмите «Новая заявка», заполните тему, категорию, кабинет, описание и число пользователей. Укажите недоступность сервиса при полном отказе. Нажмите «Создать заявку», откройте карточку, выберите исполнителя и нажмите «Назначить». После статуса «Решена» проверьте результат и нажмите «Закрыть заявку».

Исполнитель: в разделе «Мои заявки» откройте назначенное обращение. Нажмите «Взять в работу». После устранения проблемы выберите «Отметить решённой». При необходимости решённую заявку можно вернуть в работу. Чужие заявки недоступны.

Администратор: откройте «Пользователи», нажмите «Пользователь», задайте имя, уникальный логин, роль и пароль от 10 символов. В списке можно отключить запись или изменить пароль. Перед отключением исполнителя нужно переназначить незакрытые заявки. Ниже добавляются категории. В журнале действий можно проверить входы и изменения.

Поиск и импорт: в списке введите тему или исходный номер, выберите статус, категорию либо кабинет. В разделе импорта выберите CSV в UTF-8 или учебный набор, нажмите «Выполнить импорт» и проверьте журнал. Кнопка «Выгрузка» сохраняет контрольный CSV.

Сообщения об ошибках: при пустой теме заполните поле; при отказе к чужой заявке обратитесь к оператору; при истёкшей сессии войдите заново; при конфликте изменения откройте карточку повторно; при ошибке сервера сообщите администратору время и выполненную операцию.

### Карта 16 Памятка и упражнение

Памятка: сохраняйте заявку с понятной темой; назначайте только действующего исполнителя; соблюдайте последовательность статусов; при импорте смотрите итог по каждой строке; перед обновлением делайте копию; после восстановления сверяйте данные и проверяйте вход; завершайте работу кнопкой выхода.

Учебное упражнение: оператор создаёт заявку «Проверка учебного стенда» и назначает engineer. Исполнитель входит в новой сессии, видит только свои заявки, берёт обращение в работу и отмечает решённым. Оператор входит снова и закрывает обращение. Администратор проверяет историю и журнал. Ожидаются статус «Закрыта» и пять записей истории: создание, назначение и три перехода. Автоматическое выполнение этого цикла входит в test_08. Браузером дополнительно проверены входы, импорт, назначение и начало работы.
